## Remote recovery qualification

The new [remote recovery integration test](../crates/host/tests/remote_recovery.rs) passed in isolated WSL Ubuntu. It uses the real host engine, SQLite store, loopback TLS listener, certificate pinning, and public desktop client. A controlled provider supplies events and completion, so the test requires no sign-in or paid model. It does not validate provider CLI startup. The [recovery log](native-qualification/linux-remote-recovery.log) records its pass.

The test pairs a desktop, creates a session, and sends a turn. It closes the desktop's connections, finishes the turn on the host, then creates a fresh desktop client over the saved credential store. Session sync recovers the completed assistant reply. Repeating the original command returns its stored receipt without sending another provider turn.

It then closes the host engine and server and reopens the same data directory on the same loopback port. The TLS fingerprint and environment identity remain unchanged. The saved desktop pairing authenticates after a route retry, the change feed reports a new boot and reset, and the engine rebinds the existing provider conversation. An explicit follow-up completes with the original model and provider conversation identifier. Repeating either command still produces no duplicate provider turn.

The existing remote regression suite also passed 101 tests with 4 ignored tests. It checks single-use pairing links, certificate mismatch rejection, credential revocation, detached host restart, changes and session sync, and bounded transfers of transcripts larger than 16 MiB. See the [remote test log](native-qualification/linux-remote-tests.log). Strict Clippy for the new host integration target passed with `-D warnings`, recorded in the [Clippy log](native-qualification/linux-remote-clippy.log).

That Linux run exposed a command timeout defect. Killing a shell left its sleep child holding the output pipes, so a 100 ms timeout took five seconds to return. Unix commands now start in their own process group, and timeout or excessive output kills that group before collecting output. The existing timeout and output-limit regression passed after the fix. Windows production behavior is unchanged. The model-cache expiry fixture now advances a fixed clock for its exact five-minute boundary, and its regression also passed.

The subsequent Windows parallel run exposed a TCP close defect. An early credential rejection left the request upload unread and closed both socket directions, which could reset the connection before the desktop received its error. A [deterministic regression](native-qualification/remote-early-rejection-before.log) reproduced that reset on macOS too. The host now finishes sending, drains an unread upload for at most 250 ms, then closes. The complete Mac remote suite [passed 103 tests with four ignored tests](native-qualification/macos-remote-rejection-tests.log), including queued and stalled uploads, and the separate [strict Clippy run](native-qualification/macos-remote-rejection-clippy.log) passed. Windows passed the [four HTTP fixtures](native-qualification/windows-http-rejection.log) and the [complete parallel remote suite](native-qualification/windows-remote-rejection-suite.log), with 97 passing tests, no failures, and four ignored tests. The actual TLS client revocation check passed. The forced Linux [workspace run](native-qualification/linux-source-fresh-workspace.log) passed 103 remote tests with four ignored tests. Both new [HTTP rejection regressions](native-qualification/linux-source-fresh-http.log) passed by name, and [strict workspace Clippy](native-qualification/linux-source-fresh-clippy.log) passed.

Actual native remote window interaction, separate-computer reconnect, and live provider turns remain unverified by this loopback test. The separate native SSH fixture below verifies disposable loopback tunnel reconnect. No existing service or production host configuration changed.
