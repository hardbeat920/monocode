# Native relative time and collation

The retained code uses `Intl.RelativeTimeFormat(locale, { numeric: "auto" })` and no-option `String.localeCompare`. The initial native port had English relative phrases and several approximations to locale-aware ordering. The audit found reachable differences in the inbox, file ranking, grouped search and project-option ordering. Session history differs only when pin state and update time tie. Generated UUID IDs do not exhibit the observed accent and punctuation cases, but the stored summary contract accepts other string IDs.

## Retained behavior and original gaps

| Path | Retained behavior | Confirmed original native difference |
| --- | --- | --- |
| `src/features/inbox/model/githubTasks.ts`, `formatRelativeTime` | The optional locale reaches Intl. UI callers omit it and use the runtime default language. | Engine and native inbox view copies ignored locale and always returned English. |
| `src/features/files/model/fileIndex.ts` | Equal scores and equal UTF-16 lengths sort with `relative.localeCompare`. | The port compared lowercase strings, then reversed byte order. Punctuation and accents changed tied results. |
| `src/features/search/model/appSearch.ts` | Equal project scores and grouped file scores use locale-aware names and paths. | The same lowercase approximation changed tied results. Recency and score precedence were otherwise correct. |
| `src/features/sessions/data/sessionHistory.ts` | IDs break equal pin and update-time ties with locale-aware comparison. | The port used byte order for unrestricted stored IDs. |
| `src/features/inbox/model/githubTasks.ts` and `inboxFilters.ts` | Project paths, item kinds and Linear project names use locale-aware comparison. | A punctuation/digit/letter comparator disagreed on punctuation, accents and canonical equivalents. Duplicate-item project selection can change when earlier ranks tie. |

The view's comment that the retained formatter forced English was stale. The relative division sequence and rounding already matched the retained source. File ranking already measured relative path length in UTF-16. Those parts did not require replacement.

The original Node controls used default sort usage, variant sensitivity, no numeric sorting and no punctuation override. Examples include `_a` before `.a`, `a-b` after `a_b`, `é` before `f`, and equality between decomposed `e` plus a combining acute and precomposed `é`. ASCII `aB` versus `Ab` already matched the approximations and is not a reported defect. Swedish sorts `ä` after `z`; German sorts it before `z`.

## Shared native implementation

`monocode-locale` keeps ICU collators and relative formatters in a bounded thread-local cache. The engine can use it without depending on GUI or platform packages. Native handles close before the legacy Windows COM guard balances initialization. The test-support locale scope changes only the current thread and restores on unwind.

The collator enables canonical normalization and tertiary strength. It retains ICU's locale case and punctuation defaults. The sort accepts only valid `co`, `kn` and `kf` Unicode extensions. Unsupported values and unrelated collation extensions are removed. The default sort drops `co=search`, which changes actual German and Japanese comparisons in direct ICU. V8 applies the same normalization, strength and extension rules in its [collator implementation](https://raw.githubusercontent.com/v8/v8/main/src/objects/js-collator.cc).

The relative formatter uses ICU's LONG width and text-first formatting. ICU provides special phrases where its locale data has them and otherwise formats the numeric offset. The callers keep their existing unit selection and rounding. Formatter errors produce the retained empty-string result. See ICU's [relative formatter API](https://unicode-org.github.io/icu-docs/apidoc/released/icu4c/ureldatefmt_8h.html).

macOS and Windows language preferences come from the already locked `sys-locale` dependency. Linux uses ICU's process default because its `LC_ALL` and `LANG` selection matches Node Intl. The Unix `sys-locale` selector gives `LANGUAGE` priority, which selected French in a child environment where Node selected English. Explicit tags pass ICU language-tag conversion and full parsed-length validation. An additional Unicode language-prefix check rejects BCP47 grandfathered, private-only and extlang forms that Intl does not accept. Unsupported languages and `und` use the selected default. ICU supplies service-specific locale availability and negotiation. Collation uses the collator catalog, while relative time uses the DateFormat catalog as V8 does. The matched data locale replaces aliases such as `cmn`, then valid service extensions are restored. A locale such as `ccp` can be available for relative time while collation falls back to the selected default. See the [locale C APIs](https://unicode-org.github.io/icu-docs/apidoc/released/icu4c/uloc_8h.html) and [ECMA-402 locale rules](https://tc39.es/ecma402/#sec-iswellformedlanguagetag).

The undefined-locale POSIX default maps to `en-US`, as V8 does, so Linux `C` does not select POSIX binary collation. Explicit `en-US-POSIX` stays explicit. The distinction comes from V8's [default locale selector](https://raw.githubusercontent.com/v8/v8/main/src/execution/isolate.cc).

Linux shares the existing platform ICU discovery helper and retains static linkage when the development installation provides archives. macOS links the system `libicucore`. Windows loads ICU only from System32. It prefers `icu.dll` and falls back to `icuin.dll` and `icuuc.dll`, with COM initialized per calling thread for the legacy path. This avoids adding a direct `icu.dll` import that would raise the existing Windows support floor to 1903. Microsoft's [Windows ICU documentation](https://learn.microsoft.com/en-us/windows/win32/intl/international-components-for-unicode--icu-) describes the library versions and legacy COM requirement. Current Windows 11 exports and SDK libraries were inspected. This is not an actual Windows 1809 runtime pass.
